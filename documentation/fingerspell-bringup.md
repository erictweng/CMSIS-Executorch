# Fingerspell on the Alif Ensemble E8 DevKit: bring-up report

Status (2026-10-17): **the Fingerspell 24-letter model runs on the DevKit-E8's
Ethos-U85 and prints `Test_result: PASS` on the UART.** This is milestone S1
of [erictweng/fingerspell](https://github.com/erictweng/fingerspell) (private):
the model on the board, classifying a test crop built into the firmware.
Camera input comes next.

## How to reproduce (macOS)

Tools come from `vcpkg-configuration.json` through Arm Tools / vcpkg and are installed in
`~/.vcpkg/artifacts/2139c4c6/`: CMSIS-Toolbox 2.15.0, Arm Compiler 6.24 (MDK Community
license), CMake 4.2.1, Ninja 1.13.2. Packs are in `~/.cache/arm/packs`. SEGGER J-Link
V9.86a is installed, and Alif SETOOLS is in `~/Documents/app-release-exec-macos`.

```bash
# 0. Tool environment for a plain shell (CMSIS-Toolbox 2.15.0, NOT VS Code's bundled 2.13)
T=~/.vcpkg/artifacts/2139c4c6
export PATH=$T/tools.open.cmsis.pack.cmsis.toolbox/2.15.0/bin:$T/tools.kitware.cmake/4.2.1/bin:$T/tools.ninja.build.ninja/1.13.2:$PATH
export AC6_TOOLCHAIN_6_24_0=$T/compilers.arm.armclang/6.24.0/bin

# 1. Packs + cmsis-executorch.cbuild-mlops.yml for the active target
cbuild setup cmsis-executorch.csolution.yml --active DevKit-E8 --packs

# 2. Python venv (once; Python 3.10-3.13, the system python3 is 3.9)
./setup_venv.sh --uv --python 3.12

# 3. Export the model into the AI layer (~1 min)
.venv/bin/python create_ai_layer.py cmsis-executorch.cbuild-mlops.yml

# 4. Build
cbuild cmsis-executorch.csolution.yml --active DevKit-E8

# 5. Flash over the on-board J-Link (PRG USB) and start
printf 'connect\nh\nloadfile "out/cmsis-executorch/DevKit-E8/Debug/cmsis-executorch.hex"\nr\ng\nqc\n' > /tmp/load.jlink
JLinkExe -device AE822FA0E5597LS0_M55_HP -if SWD -speed 4000 -autoconnect 1 -NoGui 1 -CommandFile /tmp/load.jlink
```

Serial output: SW4 on **UART4**, `/dev/cu.usbmodem0012195786141` at 115200 8N1
(VS Code Serial Monitor). Open the port before the reset: the app prints once.

One-time board prep (already done on this board): with SW4 on **SEUART**, run the VS Code task
*Alif: Install M55_HP debug stubs (DevKit-E8, single core configuration)*, then set SW4 back
to UART4. That task writes the boot table that starts the M55_HP from `0x80200000`.

## Gotchas found on the way

1. **VS Code builds fail with `csolution.yml:120:3 schema check failed`.** CMSIS Solution
   extension 1.66 uses its bundled CMSIS-Toolbox 2.13, which doesn't know the `mlops:`
   node (added in 2.15). Newer extensions (1.67 and later) need VS Code 1.108.1 or newer.
   Workaround: build from a terminal with 2.15.0 as in step 0, or update VS Code (move
   it out of `~/Downloads` first, because macOS App Translocation blocks self-update).
2. **`get_methods() got an unexpected keyword argument 'input_shape'`.**
   `cmsis-executorch.cbuild-mlops.yml` is stale after switching branches. Rerun
   `cbuild setup` before `create_ai_layer.py`.
3. **The VS Code tasks are missing from Run Task.** The repo keeps them in `.vscode.d/tasks.json`.
   Copy that file to `.vscode/tasks.json` (git ignores it).
4. **The plain "Setup Python virtual environment" task fails with Python 3.9.** Use the
   `(uv)` variant with `3.12`.
5. **Blank console after Run.** The image had never been loaded, and the core was still
   running the debug stub (reset vector `0x80200989` instead of the app's `Reset_Handler`).
   Load the image as in step 5.
6. **The core sits in HardFault after the test (HFSR = `0x80000000`, DEBUGEVT).** This is
   expected. When `main()` returns, `_sys_exit` executes a semihosting `BKPT 0xAB`, which
   faults when no debugger is attached. All output has been printed by then. A camera
   loop should not return from `main()`.
7. **J-Link: keep SWD.** JTAG makes the generated load task block on a prompt.

## Display (DevKit-E8 LCD)

The 4.3" LCD (ILI9806E, 480x800, J21) shows what the camera sees and what the model
thinks, every frame: the 128x128 hand-box crop scaled 3x (a mirror image), the top
letter in big type with its probability and a bar (green from the decoder's 0.60
commit threshold up), the 2nd/3rd guesses, `CAM/NPU/UI` times and fps, and the
committed text. Code: `src/fs_display.cpp` (`fs_ui_init`, `fs_ui_render` from
`src/fs_api.h`), built for DevKit-E8 only (`FINGERSPELL_LCD`); details in
`board/DevKit-E8/README.md`. The live UART line gains `ui x.xms`:

    X 0.30 U 0.21 M 0.06 | cam 25.0ms pre 1.0ms npu 7.8ms ui 1.9ms | 19.5 fps

Three board fixes came with it (found on `hackathon-pico-faces`): bulk SRAM starts
64 kB above `0x02000000` so the camera ring no longer overwrites the A32 boot stub
the ATOC loads there; everything the NPU and the CDC200 read stays in SRAM0
(`SRAM0_SRAM1_COMBINED 0`, temp pool 1 MB); `main()` cleans and invalidates the
caches first, so a warm reset after a flash does not run stale lines of the
previous image. The stage timings now come from the SoC's 100 MHz REFCLK counter: the M55's DWT
cycle counter only runs while a debugger is attached, so a board that booted on its
own printed `0.0ms`. Tests: `tests/test_display.py` (`FS_HW=1` flashes and checks the
panel message, the `ui` time < 10 ms at >= 15 fps, the frame buffer changing with
the camera, and a warm reset).

## Camera exposure

The pack's MT9M114 register table leaves the sensor's auto-exposure tracking off
(`cam_aet_aemode` is set, `AE_TRACK_ALGO` 0xA804 is not): frames of a lit room had a mean
brightness of 1-5 of 255, so only a backlit screen held in front of the lens produced a
usable picture and a real hand was a black blob (this is also why the earlier "all-zero
frames" looked like a covered lens). `fs_camera_init()` now calls
`cpi->Control(CPI_CAMERA_SENSOR_AE, 1)` after the sensor configure; the probe's mean
settles at 50-65 within a few frames and real hands classify.

## Detector (BlazePalm on the Ethos-U85)

The hand no longer has to sit in the centre box: a palm detector finds it anywhere in the
320x320 frame and the classifier gets the detected hand box. Plan and design:
`documentation/hand-detection-plan.md`.

**Model.** MediaPipe `palm_detection_lite.tflite` (192x192, 290 M MACs), converted with
`ml/blazepalm_export.py` (TFLite -> ONNX -> onnx2torch -> fixed-shape graph) to
`model/blazepalm_192.pt2`; it matches the TFLite interpreter to 1e-4 on the score logits.
**Input range is [0, 1]** (`x / 255`): MediaPipe's graph for the 192 models sets
`output_tensor_float_range 0..1`. With the 2019 model's `[-1, 1]` range the detector fired on
31 % of 150 dataset images and put the palm centre inside the hand in 23 % of 150 composites;
with `[0, 1]` it fires on 76 % and 83 % with the centre inside the hand 98 % of the time.
Quantized on 100 dataset crops, against the float model on the same 300 images:

| | hit/miss agreement | mean score diff | box corners (192 px) | Vela SRAM |
|---|---|---|---|---|
| a8w8 | 274/300 | 0.04 | 2.5 px median, 5.6 px p90 | 886 KiB |
| a16w8 | 293/300 | 0.01 | 0.7 px median, 1.8 px p90 | 2306 KiB |

`model/model.py` uses a8w8 (the 1 MB temp pool holds its scratch). The two-method program
(`detect` + `classify`, both single Ethos-U delegates) needs the HP MRAM region extended to
`0x370000` (`board/DevKit-E8/RTE/Device/.../app_mem_regions.h`, same change on the AppKit-E8;
the user region shrinks to 32 kB). `detect` is exported with `quantized_io=True`: the method
takes the int8 tensor and returns the int8 head, and `create_ai_layer.py` writes the scale
and zero point of each (`DETECT_INPUT0_*`, `DETECT_OUTPUT<i>_*`) to `model_params.h`. The
first build kept ExecuTorch's portable quantize/dequantize operators at the boundary: at the
Debug build's `-O1` they took ~25 ms per frame for the 150k values, more than the NPU.

**Board side** (`src/fs_detect.c`, pure C99, host-tested): exact 5:3 box-filter resize of the
RGB565 frame to 192x192 float, anchors computed from the index (24x24x2 stride-8, then
12x12x6 stride-16), argmax + sigmoid decode of the raw head, hand box = palm box shifted
0.5 x its size from the wrist toward the middle-finger keypoint (so the rule holds whichever
way the camera is mounted), 2.6x, square, no rotation; EMA 0.5 on the box, held for up to
4 missed frames, `no hand` on the fifth; the box is cropped from the full frame with a box
filter to 128x128 (black off-frame) for the classifier. `src/app_main.cpp` runs `detect` then
`classify` per frame; `-DFS_FIXED_CENTRE_CROP` keeps the old centre crop for A/B tests. The
LCD keeps the crop view and adds an 80x80 inset of the whole frame with the box (green:
detected this frame, grey: held, red frame: no hand). Live lines:

    X 0.93 U 0.04 M 0.01 | box 112,84 96x96 s0.87 | det 3.1ms cam 2.0ms pre 0.8ms npu 4.2ms ui 1.6ms | 21.3 fps
    no hand | det 3.1ms ui 1.2ms | 21.9 fps

(`det` = resize + detector + decode, `cam` = frame wait + crop, `npu` = classifier.) Board
timings on 2026-10-17 (Debug build, scene without a hand): `det 22.9ms` = resize 5.6 ms + NPU
method 17.3 ms, `ui 1.7ms`, 18-20 fps; with a hand the classifier adds `npu 8.1ms`. The
brief's budget (det + npu < 15 ms, >= 20 fps) is **not met yet**; the detector's NPU time is
~5x Vela's ideal, the same ratio the classifier has always shown (see the handoff, section 4,
for the suspects). Tests: `tests/test_detector.py` (host: C vs
`ml/blazepalm.py` and numpy on `tests/fixtures/`; `FS_HW=1`: box or no-hand lines, fps,
warm reset).

**Open.** The classifier is still the centre-crop MobileNetV2-0.5; it should be fine-tuned on
detector-geometry crops (section 7 of `documentation/hand-detection-handoff.md`). The
detector's calibration uses dataset crops until `model/calib_detect_192.npy` exists.

## Landmarks (branch `landmark/pipeline`)

The pixel classifier is replaced by MediaPipe's hand landmark model and a keypoint MLP:
`detect` (BlazePalm) -> rotated 2.6x palm crop, fingers up (224x224 int8) -> `landmark`
(hand_landmark_lite, int8 in/out, 146 M MACs, one Ethos-U delegate) -> 21 landmarks ->
wrist-centred, size-normalised, left-mirrored features -> MLP 63-128-24 on the CPU -> the
decoder. Background, lighting and skin never reach the letter decision. Plan, decisions and
status: `documentation/landmark-plan.md`; reference `ml/handlandmark.py`; board code
`src/fs_landmark.c`; tests `tests/test_landmark.py` (host) and `tests/test_detector.py`
(board, the live lines now carry `p<presence>` and `lm <ms>`).

Numbers so far (host): exported graph vs TFLite 2e-4 px; int8 vs float landmarks 0.8 px
median / 4.2 px p90 on the crop, presence agreement 96 %; MLP 95.8 % on held-out Marxulia
landmarks (MediaPipe's pipeline); program 2,265,152 bytes; Vela scratch 1185 KiB (temp pool
1.5 MB); DevKit image MRAM 2.57 of 3.44 MB, SRAM0 3.82 of 3.94 MB. Board: detector 22.9 ms,
landmark stage 6.0 ms, 15-16 fps with a hand.

Knobs and tools from the signing sessions (`src/fs_landmark.h`, `src/fs_api.h`):

- `FS_LM_HANDEDNESS` (default RIGHT): the model's handedness score is ignored; AUTO mirrors
  by it as before. Set LEFT for a left-handed signer. The datasets keep AUTO (clean photos,
  reliable score).
- `FS_LM_PRESENCE` 0.5 / `FS_LM_PRESENCE_HOLD` 0.25 / `FS_LM_HOLD_FRAMES` 5: a tracked hand
  survives up to 5 frames of presence in [0.25, 0.5). A far hand (box ~55 px) scores 0.2-0.4
  for a frame or two; signing with the box >= 75 px avoids it altogether.
- Motion letters: `motion_threshold` 1.0 hand sizes of fingertip displacement from where the
  D / I hold began (not a path sum); Z / J commit when reached; the panel's guess line shows
  `D HELD: MOVE FOR Z  PATH n%` while pending.
- `tests/board_telemetry.py --handedness` (flips, uncertain frames), `tests/capture_keypoints.py
  --letter R --seconds 10` (the board's landmarks for a letter -> `model/keypoints_board_live.npz`),
  then `ml/keypoint_train.py model/keypoints_marxulia.npz model/keypoints_marxulia_board.npz
  model/keypoints_board_live.npz --upweight board-live=4`, `create_ai_layer.py`, build, flash.

## Decoder (temporal averaging, branch `landmark/pipeline`)

`src/fs_decoder.c` turns the per-frame probabilities into text. It no longer decides each
frame on its own (spec: `documentation/temporal-average-plan.md`): the 24 probabilities are
averaged over frames and every rule reads the average. The parameters, all in
`fs_decoder_cfg_t` (`src/fs_api.h`), and what to tune when:

| Parameter | Default | Tune when |
|---|---|---|
| `prob_alpha` | 0.4 | letter changes feel laggy: raise toward 0.5; spam remains: lower toward 0.3. 1.0 turns averaging off |
| `commit_threshold` | 0.60 | letters sit at 0.5-0.6 on a real hand: lower to 0.50 (safe once averaging is on) |
| `hold_threshold` | 0.45 | the live letter drops out mid-hold: lower (keep under `commit_threshold`; 0 = no hysteresis) |
| `commit_frames` | 3 | first letter too slow: 2 is safe on the averaged stream |
| `release_ms` | 300 | double letters ("LL") need a shorter or longer bounce of the hand out of view |
| `space_ms` | 1000 | spaces come too early or late after the hand drops |

Two more averages run before the decoder: the crop geometry the landmark model sees
(`FS_LM_CROP_SMOOTH` 0.5, `src/fs_landmark.h`) and the MLP features (`FS_LM_SMOOTH` 0.5).
Both restart when the hand is lost. Expected budget at 15 fps: first letter on screen in
about 7 frames (450 ms), a change to a new letter in 5-7 frames.

Rules worth knowing when reading `decoder:` lines or `tests/board_telemetry.py`: the same
letter repeats only after the hand left the frame for `release_ms` (a confidence dip never
re-arms it); the displayed confidence is the averaged one; `g_fs_tele[1]` is still the raw
MLP top-1 probability. Host tests: `python3 -m unittest tests.test_decoder_host` (no venv).

## Voice (keyword spotting, branch `voice/kws`)

The hearing person answers the signer out loud: the board's I2S MEMS microphones feed a
keyword-spotting model on the Ethos-U85 and the word appears as `> YES` on the last row of
the words card, in amber, while the signer's text keeps three rows. Vocabulary: yes, no, up,
down, left, right, on, off, stop, go (plus silence and unknown, never shown). Plan and
findings: `documentation/voice-plan-status.md`; the brief `voice-plan.md`.

```
I2S3 mic (IRQ, 16 kHz mono)  ->  fs_voice_capture.c ring 1.5 s (DTCM)
  ->  fs_voice.c MFCC per 20 ms stride (M55)  ->  rolling 49x10 int8 window
  ->  method "kws" every 0.5 s (DS-CNN small, Ethos-U85)  ->  softmax, threshold 0.7, 1 s refractory
  ->  "voice: yes 0.91 npu x.xms" on the UART, the reply row on the LCD
```

- **Model.** Arm ML-Zoo `ds_cnn_small` (Apache-2.0), the MLPerf Tiny DS-CNN: 23.8 k
  parameters, 2.7 M MACs. No PyTorch checkpoint exists anywhere, so `ml/kws_tflite_to_npz.py`
  (TensorFlow, tools venv) pulls the trained weights out of the fp32 TFLite file and
  `ml/kws_export.py` loads them into a PyTorch module that reproduces TF's `SAME` padding
  (the DS-CNN in `executorch/examples/models/mlperf_tiny` pads one row differently) and
  saves `model/ds_cnn_kws.pt2`; it matches the TFLite interpreter to 3.5e-6 on the 36
  reference clips. The `kws` method in `model/model.py` is a8w8 with `quantized_io`
  (`KWS_INPUT0_*`, `KWS_OUTPUT0_*` in `model_params.h`; the export gave input scale 1.094,
  zero point 98, like ML-Zoo's own int8 model), calibrated on `model/calib_kws.npy` (100
  Speech Commands v2 test clips). Strict export: one Ethos-U delegate, no CPU operators,
  Vela SRAM 23.6 KiB, weights 29.6 KiB; the three-method program is 2,299,024 bytes.
- **Front end.** `ml/kws.py` (numpy) reproduces TensorFlow's `audio_spectrogram` + `mfcc`
  as the model was trained: 640-sample periodic Hann every 320, 1024-point FFT, 40 HTK mel
  channels 20..4000 Hz on the magnitude spectrum, log with a 1e-12 floor, DCT-II scaled by
  sqrt(2/40), 10 coefficients, no normalisation; it matches TF to 2.5e-5 on 36 clips
  (`tests/fixtures/kws_ref.npz` holds TF's own output). `src/fs_voice.c` (C99, float
  radix-2 FFT, tables built at init) matches TF to 1.1e-4 and quantizes identically to the
  reference in every chunk size. One frame per 20 ms of audio, computed as the samples
  arrive, so the loop never does a 49-frame burst.
- **Microphone.** The DevKit-E8 has two I2S MEMS mics (U14/U16) on I2S3 of the HP core,
  pins already muxed; `src/fs_voice_capture.c` drives `Driver_SAI3` directly in IRQ mode
  (master, I2S protocol, 16-bit, `ARM_SAI_MONO_MODE`, SCLK 76.8 MHz / 75 = 1.024 MHz after
  enabling HFOSCx2 through the SE services), one 320-sample `Receive()` re-armed from the
  callback into a 75-block ring in DTCM (48 KB). Counters `g_fs_voice_*` are readable over
  J-Link. LPI2S/LPPDM are HE-only; the PDM mics (channels 4/5) are the fallback.
- **Accuracy of the port with our front end** (`ml/kws_eval.py`, 100 Speech Commands v2
  test clips per class, host): 89.1 % top-1 float, 88.8 % with the board's int8 input
  quantization; the ten words score 88-98 %, `_silence_` only 48 % (noise snippets read as
  down/off/yes). At the 0.7 threshold 5 of 100 noise clips and 14 of 100 unknown-word clips
  would be accepted as a word; all-zero audio is `silence` at 1.0. Knobs: `kVoiceThreshold`,
  `kVoiceRefractoryMs` in `app_main.cpp`; a two-consecutive-windows rule is the next step if
  the room triggers words.
- **Build.** `APP_VOICE` in the DevKit-E8 layer (remove it for the camera-only build),
  `CMSIS Driver:SAI` component; `fs_voice.c` builds for every target, `fs_voice_capture.c`
  for the DevKit only. Image with voice: code 194,016 B, RO 2,429,132 B, ZI 4,804,964 B; MRAM
  free 973 KB, DTCM free 244 KB, SRAM0 unchanged (118 KB free). Boot prints
  `Voice self-test: yes 0.xx (expected yes)` and `Voice_test: PASS` (a TF-computed "yes"
  clip through the kws method; independent of `Test_result`), then
  `voice capture init OK (I2S3 16 kHz mono 16-bit)`.
- **Tests.** `tests/test_voice.py`: host (C vs TF and numpy, stream quantization, softmax,
  decision rule, the pt2 vs the interpreter, the generated parameters) and `FS_HW=1`
  (capture running, blocks at 50/s, no overruns, frames and inferences advancing, ms per
  frame and per inference, level not stuck) over J-Link; `tests/voice_check.py` watches the
  level, the top word and the accepted words live for a person saying the words.
- **Board numbers:** pending the first flash (see the status file).
